# exp/t3_access/ — T3 接入握手方案对比（3 方案 × 3 场景，双轨）

> 标准与 T2 一致：**1 最新已落地现代化基线 + 1 贴合项目的最新论文方法 + 本项目自身**。
> 最后更新：2026-09-16（第 3 轮：新增变量隔离对照 + 时延口径修正）

## 一、三个方案

| `rach_scheme` | 角色 | 来源 | 机制 | 容量单位 |
|---|---|---|---|---|
| `twostep_precomp` | **本项目** | 本方案 | 两步 RACH + GNSS/星历开环 **TA 预补偿** → 免前导竞争、握手短 | 1 |
| `rel17_4step` | **已落地基线** | 3GPP Rel-17 NTN（2022） | 四步 RACH：前导竞争 + RAR 窗口 + 竞争解决定时器 + 4×几何往返 | 2 |
| `msgarep_2step` | **论文方法** | T. Kim, S. H. Chae, I. Bang, "Two-Step Random Access With Message Replication for Low-Earth Orbit Satellite Networks," **IEEE WCL** 14(4):1134–1138, 2025. DOI:10.1109/LWC.2025.3535231 | 两步 RACH，但**存在 MsgA 前导冲突**；发 M=4 份副本，任一份避开冲突即成功（副本分集） | M=4 |

**对比轴**：**4 步 vs 2 步**（时延）、**预补偿消除冲突源 vs 副本分集抗冲突**（成功率路径）——论文方法与本项目**机制正交**，不会被评审判为「本项目消融」。

## 二、结果（oneweb / seed=42 / 双轨，格式 `Python / ns-3`）

### 场景 ① `wenchuan_storm2` — 窄带（`rach_capacity=4`）：资源效率主导

| 指标 | twostep_precomp（本项目） | rel17_4step（已落地） | msgarep_2step（论文） |
|---|---|---|---|
| 接入时延均值_ms | **193.5 / 222.3** | 607.6 / 673 | 116.5 / 266.1 |
| 接入时延P95_ms | **846.7 / 913.7** | 1191 / 1363 | 485.9 / 992.9 |
| 接入成功率 | **0.7234 / 0.6987** | 0.4083 / 0.4445 | 0.158 / 0.2052 |
| RACH吞吐_终端每秒 | **0.2261 / 0.2222** | 0.1276 / 0.1414 | 0.0494 / 0.0653 |

→ 容量受限时**资源效率主导**：本项目最优；msgarep 因 ×M=4 资源开销最差。
→ 相对**已落地 Rel-17 四步**：成功率 **+0.315**（0.7234 vs 0.4083）、时延 **−68%**。

### 场景 ② `wenchuan_storm2_wide` — 容量不受限（`rach_capacity=256`）：隔离「资源效率」

| 指标 | twostep_precomp | rel17_4step | msgarep_2step |
|---|---|---|---|
| 接入时延均值_ms | **12.42 / 12.40** | 399.5 / 403.5 | 13.31 / 14.76 |
| 接入成功率 | 1 / 1 | 1 / 1 | 1 / 1 |

→ **容量不 binding 时三方案成功率均 1.0**（该规模下前导冲突亦不 binding），但已可证明：**msgarep 的窄带劣势纯来自 ×M 资源代价**（时延由 116.5/266.1 恢复到 13.31/14.76 ms，≈本项目 12.4 ms），**非其机制无效**。`rel17_4step` 仍 ~400 ms（四步结构的固有几何/定时器代价）。

### 场景 ③ `wenchuan_storm2_contend` — 高冲突（容量不受限 + 前导码 64→8）：隔离「前导冲突」

| 指标 | twostep_precomp | rel17_4step | msgarep_2step |
|---|---|---|---|
| 接入时延均值_ms | **12.42 / 12.39** | 498.1 / 525 | 183.9 / 228 |
| 接入成功率 | **1 / 1** | 0.9561 / 0.9424 | **0.8025 / 0.7651** |
| RACH吞吐_终端每秒 | **0.3125 / 0.3181** | 0.2988 / 0.2997 | 0.2508 / 0.2433 |

→ ★**与预期相反，据实记录**★：把前导冲突变为主导失败源后，**msgarep 成功率反而低于 `rel17_4step`**（0.80 vs 0.96，双轨一致）。

## 三、关键建模假设：容量单位 `RACH_SLOT_UNITS`（务必了解）

`_slot_ok()`（星上时隙准入，`rach_capacity` 每 10ms 时隙）按方案扣减容量单位：

| 方案 | 单位 | 依据 |
|---|---|---|
| `twostep_precomp` | 1 | MsgA 一次前导+载荷占用 |
| `rel17_4step` | 2 | Msg1 前导 + Msg3 竞争解决两次占用 |
| `msgarep_2step` | M=4 | M 份 MsgA 副本各占一份资源（副本分集的资源代价） |

**为什么必须有这个区分**：改之前成功率只由时隙容量上限决定、**与接入方案无关**（实测三方案均 0.7234），T3 无法体现方案差异。

**敏感度实测（诚实披露）**：把 `msgarep_2step` 的容量单位改回 **1**（"副本不额外耗资源"的理想假设）再跑，得 **成功率 0.7217 / 时延 201.6 ms**（≈ 本项目 0.7234 / 193.5）。→ 即 **msgarep 的低成功率来自「×M 资源开销」，不是来自冲突模型**。

## 四、结论：副本分集在「副本各占独立资源」的忠实解释下不占优（★核心发现★）

三个场景构成**逐步隔离变量**的实证链：

| 变量 | 本项目 | rel17_4step | msgarep_2step |
|---|---|---|---|
| 窄带（容量 + 冲突均受限） | 0.7234 | 0.4083 | 0.158 |
| 容量不受限 | 1 | 1 | 1 |
| 容量不受限 + 高冲突 | 1 | 0.9561 | **0.8025（低于 rel17）** |

- **机制解释**：本项目对副本分集采用**忠实资源记账**——M=4 份副本各占**独立**前导资源（`sim/protocol.py` 的 `_preamble_contend(force=True)` 循环 + `RACH_SLOT_UNITS=4`）。因此副本的**资源外部性**（多占 4 份前导、把整体冲突水平推高）**超过了**其**分集增益**。
- **诚实定位**：这是**实证结论**，不是实现缺陷；它使 T3 的对比**不靠踩低论文基线取胜**——本项目在三个场景下均**不劣于**论文方法，且最差场景下差距来自可解释的机制（预补偿消除冲突 vs 副本以资源换分集）。
- **解释差异披露**：若 Kim et al. 原意是「副本**复用同一前导**、仅在时/频上重复载荷」，则资源外部性会小得多、分集增益可能转正。本项目采用「独立前导」解释并**如实标注**，未做该替代解释的对照实验（属可选扩展）。

## 五、时延口径（★必读★）

`接入时延均值_ms` 按 `docs/仿真接口约定.md`（契约 2.1）**仅统计成功终端**（失败事件 `value_ms=-1` 不计入）。三方案成功率差异大时存在**幸存者偏差**：
- 窄带场景 Python 轨 msgarep 时延 116.5 ms **看似最低**，实因其成功率仅 0.158、均值只覆盖少数"快速成功"终端；ns-3 轨同场景 msgarep 为 266.1 ms → **两轨时延排序不一致**，即该偏差已使结论不可跨轨复现。
- 故**跨方案比较必须并读** `接入成功率` 与 `RACH吞吐_终端每秒`（二者无该偏差，两轨排序一致）。
- 原文档中「两轨排序逐项一致／本项目最短」的表述**对时延不成立，已更正**。

## 八、注意事项（避免误判）

- 本项目 `twostep_precomp` 建模为**免前导竞争**（TA 预补偿消除定时获取往返，是本项目核心简化假设）；`msgarep_2step` 显式建模 **MsgA 竞争 + 副本分集**。
- `rel17_4step` 的附加时延由机理式 `step4_extra_ms()` 给出（RAR 窗口 + 竞争解决定时器 + 4×斜距），**非无源常量**。
- 三方案共用同一套可见窗（方案 A 网格窗，见 `../方案A_网格窗实现说明.md`），故成功率/时延可比。
- 本实验**不涉及 T4 认证**（T4 为真实 HMAC 实现，见 `sim/auth.py`），T3 结论不借 T4 数字撑场。
